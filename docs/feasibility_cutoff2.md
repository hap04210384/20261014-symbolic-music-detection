# cutoff=2 挖掘可行性实测（2026-10-12）

## 结论（硬事实）

**设计文档 §2 的 σ=2/(N+1) 全库挖掘协议在本机实测不可行，且不是实现问题，是数据组合爆炸。**

### 证据 1：引擎实测（TensorFIM bitmap，RTX 3060 Ti + i9-12900）

| N（含查询） | σ | 结果 |
|---|---|---|
| 21 | 0.5 | 0.2 秒完成（0 MFI） |
| 21 | 2/21=0.0952 | **>120 秒未完成** |
| 51 | 2/51 | >280 秒未完成 |
| 301 | 2/301 | >290 秒未完成 |
| 1001 | 2/1001 | >290 秒未完成（仅预处理+GPU基准通过） |

引擎自身基准：该数据规模下单次频率核调用 GPU 比 CPU 慢 50 倍
（GPUpercentage 1.9%），枚举节点数爆炸是主因。

### 证据 2：频繁对计数（纯 Python 精确统计，与引擎同口径 freq≥2）

| N | cutoff=2 幸存项 | 不同对 | freq≥2 对 |
|---|---|---|---|
| 20 | 1,538 | 511,719 | **96,195** |
| 100 | 6,918 | 7,620,638 | **2,366,075** |
| 300 | 13,194 | 29,225,259 | **11,299,887** |

仅 **2 项集** 层面在 N=300 就达 1130 万且随 N 超线性增长；3 项集以上更糟。
真实音乐在项级（音高×时值×音距×力度）的偶发重复是爆炸根源。
N=174,300 时 2 项集将超 10⁹ 量级，任何枚举式 MFI 算法都不可能完成。

### 推论

- GivenThreshold σ=2/(N+1) 协议 **无法产出 E4/E1/E2 的任何数据**；
- AnyFIM-Anytime 的 20 阶段截断只保留 top-20 高频项（在百万级语料上
  频率数十万），freq=2 的复制片段项**必然被阶段阈值剪掉**，
  anytime 模式同样给不出召回保证；
- 这是"枚举式挖掘"范式的固有边界，不是调参能解决的。

## 仍成立的核心资产（卖点骨架不动）

检测的数学本质不是"枚举频繁项集"，而是**集合包含**：
命中 ⟺ 片段 S ⊆ Q 且 ∃C_i: S ⊆ C_i。
- 召回保证来自"verbatim 复制 ⟹ S 逐项包含"这一构造事实，与挖掘算法无关；
- 免阈值 anytime 的保证对象是**候选空间覆盖比例**（已验证片段 / 应验证片段），
  不需要引擎的阶段机制；
- 引擎（AnyFIM/TensorFIM）的位图内核仍是底层发动机思想（位图与、批量波），
  但其"枚举 MFIs"的调用方式在本任务不可行。
